3. 命名与登记

## 1. 原则

- 对话承载一个阶段责任，文件承载跨阶段事实。
- 按阶段逐步创建，不预创建尚无冻结输入的下游对话。
- 每个对话从固定文件和 Git 提交恢复，不依赖旧聊天摘要。
- 独立验收对话不继承开发者的主观结论；只提供合同、固定提交和原始证据索引。
- 对话数量由独立责任决定，不由“看起来专业”决定。

## 2. 创建时机

### 产品与设计对话

项目初始提案获确认后创建。输入为项目简报、现状审计和素材索引；输出为 PRD/差量需求、确认设计、实现与验收合同。

### 开发总控对话

只在 S3 合同冻结后创建。若是既有版本系列，还必须等待版本治理返回 `candidate_materialized`；对话工作目录必须是该 `active_version_root`。输入为固定基线、必读文件、工作包、文件所有权、验证命令和禁止事项。

创建或生成开发启动包前，运行 `validate_project_state.py <project-root> --gate handoff`。任何状态顺序、路径、PRD/UI/AGENTS/PROJECT_STATE 漂移或未追踪需求都会阻止交接；用户要求“先创建再补”不能绕过。

### 独立验收对话

只在候选提交固定、开发报告和证据索引存在后创建。不得要求它相信“全部通过”；要求从合同逐项复验。

独立验收返回 `accepted / rejected`，不得直接把版本设为 `current_approved`。总控记录独立的版本批准后，再让版本治理执行全部前序归档。

验收报告必须写入文件并引用固定候选点和证据 manifest。用户口头声称“已查看验收”而项目内没有对应报告时，保持 `acceptance pending`。

### 专项对话

仅在具备独立目标、输入、文件所有权和完成条件时创建，例如安全审查、数据迁移、视觉系统或硬件台架验证。

## 3. 命名与登记

使用：`<项目>｜<版本>｜<序号> <责任>`。

示例：

- `NOTE1｜V0.3｜01 产品与设计`
- `NOTE1｜V0.3｜02 开发总控`
- `NOTE1｜V0.3｜03 独立验收`
- `NOTE1｜V0.3｜专项 UI 视觉系统`

在 `SESSION_REGISTRY.md` 记录：标题、职责、状态、工作目录、分支/固定点、必读入口、启动 Prompt、创建日期和关闭日期。为兼容既有项目保留文件名；在 WorkBuddy 中把它理解为任务/对话登记表。只有平台实际返回正式 task/session ID 时才填写 ID。

WorkBuddy 5.3.11 的当前验证基线未向本 Skill 暴露可调用的任务创建或分叉 API。默认流程是：

1. 确认项目、阶段、工作目录和是否为 Git 仓库；用户未确认项目根时保留 `<待用户确认的项目根>`，不生成用户主目录、时间戳目录或 WorkBuddy 临时目录作为默认值；
2. 运行适用 gate，确认启动输入已冻结且路径有效；
3. 生成标题、固定起点、完整启动 Prompt 和必读文件；
4. 标记 `task plan ready / task creation unsupported`；
5. 由用户在 WorkBuddy UI 中手动新建任务并粘贴 Prompt；
6. 用户提供真实任务 ID 或平台后来返回 ID 时再登记；不得把计划项、标题或临时标识写成真实 ID。

当前也不承诺自动创建 Git 分支或 worktree。需要隔离时，优先提出新的本地候选目录/staging；若项目必须使用 worktree，先检查 Git 状态并输出待用户确认的本地命令，只有命令实际成功后才能登记其路径。未来 WorkBuddy 版本若真实暴露语义明确的任务创建工具，仍须先做 capability detection 和用户授权，再调用并记录真实结果。

生成启动 Prompt 前重新解析当前项目根，检查所有已确认绝对路径存在。尚未确认项目根时使用 `<project-root>` 和 `<skill-dir>` 占位符，并把路径确认列为启动条件；不得用发布者机器的安装目录、WorkBuddy 会话临时目录或自行拼接的用户主目录替代。项目移动后先提出路径重绑定并更新 `PROJECT_STATE.md`、`AGENTS.md` 和登记表，再重新运行 status gate；不得继续发放含旧路径的启动包。

## 4. 启动包

每个启动包必须包含：

1. 角色和唯一目标；
2. 项目根目录、版本、分支和固定起点；
3. 必读文件清单及权威顺序；
4. 已确认事实、非目标和不可回归能力；
5. 允许/禁止修改范围；
6. 阶段交付物和逐项验收标准；
7. 测试、运行验证和证据要求；
8. 遇到冲突、缺失或范围变化时的停止条件；
9. 回报格式；
10. 不依赖旧聊天摘要的要求。

启动后先要求下游复述：目标、范围、关键合同、禁止事项、验证方式和开放问题。复述不一致时先纠正，不进入实施。

## 5. 子智能体

开发总控按可独立交付的工作包委派。每个任务明确：目标、拥有的文件/模块、只读依赖、不可修改范围、基线、验收、测试和返回内容。

规则：

- 不让多个工作者同时拥有同一文件；共享文件由集成负责人修改。
- 并行任务必须依赖独立；存在依赖时按波次执行。
- 工作者知道还有其他人在仓库中，不撤销或覆盖他人改动。
- 每个工作包先做规格符合性检查，再做代码质量检查。
- 开发总控负责跨模块整合和真实关键路径，不把子智能体“完成”直接视为版本完成。
- 产品/架构决策、跨任务优先级和最终验收不委派给孤立工作者。

## 6. 上下文控制

- 一个对话只处理一个版本阶段或一个明确缺陷批次。
- 阶段完成后写交接文件，并建议用户在 WorkBuddy 中开启干净任务，不靠无限续聊。
- 长任务按可验证增量提交；必要时写暂停/恢复点。
- 下游只加载相关权威文件，不把整个历史证据库塞入上下文。
- 发现对话开始重复、忘记边界或无法区分事实时，停止继续堆上下文，更新文件化状态并切换干净对话。
