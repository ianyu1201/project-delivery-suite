# 质量门禁、证据与独立验收

## 证据层级

证据按要证明的结论选择：静态检查/构建证明代码与构建事实，单元测试证明局部逻辑，集成测试/状态断言证明交互和数据行为，截图证明外观，视频证明时序。目标环境运行覆盖环境相关结论；独立复验增加独立性，但不自动覆盖其他检查。叙述或旧摘要只能提供线索。

## 风险驱动验证

为每个工作包标记风险：产品逻辑、数据、导航、视觉、无障碍、性能、安全、迁移、硬件。按风险选择门禁，不机械要求所有项目运行同一套测试。

最低要求：

- 修改代码：项目要求及影响范围内的必要测试、静态检查或构建；明确说明不适用项，不要求局部文档变更执行全套构建；
- 修改导航/数据/手势：自动化路径或可重复状态断言；
- 修改视觉/系统栏/动画：目标环境视觉抽样；
- 修改持久化/迁移：旧数据、失败和恢复场景；
- 控制实体设备：仿真/台架/安全停止/实机分层证据。

## 缺陷等级

- **P0**：数据不可恢复、严重安全/隐私、核心系统不可用或实体安全风险。
- **P1**：核心闭环无法完成、主要入口失效、稳定复现崩溃或关键结果错误。
- **P2**：重要但有绕行的体验、视觉、兼容或性能问题。
- **P3**：低影响瑕疵、优化建议或未来改进。

版本候选不得含未处置 P0/P1。P2/P3 是否允许由产品/发布责任人明确决定，不得静默遗留。

## 证据清单

截图前先建立覆盖矩阵：`coverage group → proof type → covered contract IDs → evidence equivalence key → capture checkpoint → planned artifact`。行为类要求不要为了方便而塞进截图组。

证据等价键至少包含：commit/build、页面/路由、UI 状态、数据夹具、设备/OS/viewport、方向、外观、语言、字号/无障碍设置、滚动/焦点/键盘/权限和时变状态。键完全一致的视觉要求共用一次截图；不同键可以在一次批量运行中连续采集，但仍是不同证据。

建立 manifest，每项包含：

- evidence ID；
- covered requirement/contract IDs；
- evidence equivalence key；
- commit 和构建；
- 环境/设备/OS；
- 初始数据；
- 操作步骤；
- 预期与实际；
- pass/fail/pending；
- 原始文件；
- 采集者和时间；
- 限制和未覆盖项。
- valid / invalidated 状态及失效原因。

截图和视频使用稳定命名，例如：`EVID-V03-UI-014-search-empty-iphone-se-max-text.png`。不要只保存“final2.png”。

提交变化时先做影响分析。渲染源码、共享壳层、设计令牌、依赖/锁文件、构建配置、夹具或运行环境变化时重采受影响组；无法证明无影响时重采。仅文档变化等情形，若这些输入及视觉等价键其余部分不变，可继承原证据。保留原 capture commit/build，另记录适用的新提交、比较范围、输入哈希/产物身份、分析依据、复核者和限制；不得把旧截图改标为新采集。最终验收允许经核实的继承链，链上任一输入不明则不得复用。

更新适用记录时区分“用户提供的比较结论”与“本轮实际核对的比较产物”。用户已明确给出无影响结论时，可据此记录继承适用性，同时注明来源、实际复核者及本轮未执行的检查；不得声称亲自计算或核验了未取得的哈希。缺少原始证据、比较产物或身份指针时，列明待补项并将最终验收有效性保持 pending，不以一条 `valid` 掩盖审计链缺口，也不为补记录重复采集或重复索要已有授权。

## 独立验收

独立验收用于正式版本、项目要求、用户请求或高风险交付；局部交付未运行时明确 not performed。验收者接收：固定提交、合同、非回归矩阵、运行方式、证据索引和已知问题；不接收开发者对结果的主观结论作为事实。

验收顺序：

1. 确认提交、环境和工作区干净度；
2. 检查合同完整性与需求追踪；
3. 运行自动化门禁；
4. 复验关键用户路径和高风险场景；
5. 抽查开发证据真实性与对应关系；
6. 对视觉风险比较确认基线；
7. 输出逐项 `pass/fail/pending/not-applicable`；
8. 给出接受、条件接受或拒绝建议。

失败时创建限定范围的修复轮次；修复后重新固定提交并复验受影响合同和非回归范围。

## 关闭用语

推荐：`本版本合同范围已完成；无已知 P0/P1；约定门禁与关键运行路径在所列环境通过；未验证项和允许遗留项见报告。`

禁止：`绝对没有 Bug`、`所有设备肯定正常`、`测试都过了所以 UI 没问题`。
