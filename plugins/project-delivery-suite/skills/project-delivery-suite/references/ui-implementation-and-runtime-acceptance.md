## 1. 为什么 PRD 和参考图仍不够

PRD 定义用户问题、范围和体验意图；参考图展示某个状态的视觉结果。开发还需要知道布局关系如何适配不同设备、系统区域由谁负责、状态如何变化、手势如何触发、数据如何保存以及怎样证明运行结果正确。

因此对任何 UI 项目强制建立三层合同：

```text
产品合同（what/why）
        ↓
实现约束（不得破坏的空间、状态和行为关系）
        ↓
运行验收合同（在真实目标环境如何观察和判定）
```

不要把“使用某个 UI Skill”当作其中任何一层的替代品。

## 2. 输入可信度

建立输入登记：

| 输入 | 身份 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| PRD | 已确认/草案 | 产品范围和意图 | 精确布局实现 |
| 候选图 | candidate | 视觉方向可能性 | 最终 UI |
| 确认图 | confirmed baseline | 指定页面/状态的视觉目标 | 未展示状态和动态行为 |
| 当前代码 | implementation fact | 当前实现 | 最终需求 |
| 运行截图/视频 | runtime evidence | 指定构建和环境观察 | 其他设备/状态 |

若没有冻结新视觉，合同必须明确“无确认视觉基线”，不允许开发者从候选图自行选稿。

## 3. 实现约束

为每个页面或关键组件记录：

### A. 页面身份

- 页面目标和用户此刻的主要任务；
- 主操作、次操作和退出路径；
- 所属导航层级和进入/离开条件。

### B. 结构与系统区域所有权

- 根容器、滚动容器、内容容器、覆盖层；
- 状态栏、安全区、导航栏、Tab 栏、键盘避让分别由系统还是页面负责；
- 每个顶部/底部 inset 只能有一个所有者，禁止重复补偿；
- 内容是否允许延伸到系统区域下方。

### C. 空间关系

优先写关系而不是孤立像素：

- 对齐锚点；
- 组件之间的固定/范围间距；
- 最小/最大尺寸和宽高关系；
- 哪个区域可以伸缩，伸缩上下限；
- 内容不足和内容溢出时的行为；
- 滚动、固定、吸附、分页和遮挡规则。

把约束标为：`invariant`（必须恒定）、`range`（允许范围）、`relation`（相对关系）、`adaptive`（环境规则）。不要使用无上限弹性空白、硬编码偏移或固定高度掩盖未解决的布局关系。

### D. 视觉令牌与层级

- 字体语义、颜色角色、材质、圆角、描边、阴影；
- 强调层级和可点击性线索；
- 系统组件与自定义组件边界；
- 深色模式、降低透明度、增强对比度等适配（如适用）。

### E. 状态矩阵

至少判断：首次、默认、空、少量、长内容、加载、错误、离线（如适用）、编辑、禁用、处理中、成功、删除/撤销、恢复和历史数据兼容。每个状态写触发条件、可见内容、可用动作、数据变化和离开方式。

### F. 交互与手势

- 点击目标、触发区域和优先级；
- 手势方向、起点限制、阈值、取消、冲突和动画反馈；
- 导航目标和返回行为；
- 破坏性动作确认/撤销；
- 连点、快速切换、中断动画和键盘显示时的行为。

### G. 数据与持久化

- 动作改变哪些状态；
- 何时写入、失败如何反馈；
- 重启/返回/跨页后是否保留；
- 旧版本数据如何显示；
- 预览数据与正式数据严格隔离。

### H. 无障碍与设备适配

- 最小点击目标；
- VoiceOver/语义树顺序、标签、值和动作；
- 动态字体默认与最大辅助字号；
- 窄屏、键盘、旋转（若支持）、减少动态效果；
- 颜色不能作为唯一信息来源。

### I. 非回归与禁止事项

- 上一版本不可丢失能力；
- 不可改变的术语、数据和导航合同；
- 禁止用占位内容、静态截图、只适配单一设备、隐藏错误、吞掉手势或无证据重写共享壳层来“通过视觉”。

## 4. 运行验收

每项验收写成：

```text
Given 环境和初始数据
When 用户实际执行动作
Then 可观察界面、导航、数据和反馈
Evidence 需要保存的证据
```

### 最低场景

- 冷启动和已有数据启动；
- 每条一级导航入口；
- 核心闭环从创建到最终成果；
- 关键手势的成功、未过阈值取消和冲突；
- 错误/空/长内容；
- 退出重进后的持久化；
- 默认字号、最大辅助字号和目标窄屏；
- 合同指定的系统版本/设备。

### 验证方法优先级

- 编译、单元测试、静态检查：证明代码层事实，不截图。
- 导航、数据、状态和手势：优先自动化测试、可访问性树和状态断言。
- 布局、系统栏、材质、动画反馈和视觉层级：使用最小充分截图/视频，并与确认基线比较。
- 同一页面连续修改只保留首轮风险证据和最终证据；把多个设备/字号批量取证。
- 视觉差异为零也不能证明点击、数据和导航正确；行为测试通过也不能证明视觉正确。

## 5. 视觉证据覆盖与批量取证

在打开模拟器或设备截图前，先汇总本轮全部合同、任务和非回归项，建立“视觉证据覆盖矩阵”。先判断每项应该由自动化、状态断言、日志、视频还是截图证明；只有真正存在视觉风险的项目进入截图计划。

为每个计划截图建立证据等价键：

```text
commit/build + page/route + UI state + data fixture
+ device/OS/viewport/orientation
+ appearance/locale/font/accessibility settings
+ scroll/focus/keyboard/permission/time-sensitive state
```

只有等价键全部相同、且要求观察的是同一可见表面时，才允许复用同一张截图。一个 Evidence ID 可以关联多个合同或任务 ID；不得因为任务分批下发而对同一等价键重复截图。

执行顺序：

1. 汇总全部待验证项并标记所需证据类型；
2. 按证据等价键分组；
3. 选择能覆盖最多要求、同时仍清晰可判定的最小截图集合；
4. 把默认字号、最大辅助字号、窄屏、深浅色等不同等价键安排为一次批量运行，而不是混成一张图；
5. 在集成稳定检查点或最终候选提交统一采集；
6. 在 manifest 中用同一 Evidence ID 关联所有被覆盖的合同 ID；
7. 相关实现或环境变化时，把该证据组标为 invalidated，并只重采受影响组。

失效条件至少包括：候选 commit/build 改变；页面或共享壳层、设计令牌、安全区、导航、数据夹具发生相关修改；设备/OS、字号、语言、外观、权限、键盘、焦点或滚动状态改变。开发过程可依据影响分析只重采受影响组；最终验收证据必须对应最终候选 commit/build，不得沿用旧提交截图。

不要过度复用：截图不能证明点击、导航、手势阈值、动画时序、数据写入和重启持久化；这些仍使用自动化、日志、状态断言或视频。画面包含动态时间、随机数据或远端内容时，固定数据夹具或显式记录限制。

### 容差

只对经确认基线中的关键锚点设置容差。系统字体渲染、动态内容和材质允许环境差异；必须一致的关系由合同明确。不要把所有界面都强制像素级一致，也不要用“看起来差不多”代替关键关系。

## 6. 证据与关闭标准

每份证据关联：项目、版本、commit、构建配置、设备、OS、数据集、操作步骤、预期、实际、结果、文件路径和采集时间。候选图不得存入运行证据目录。

页面关闭需满足：

- 所有 `must` 实现约束可追踪到代码/测试/运行证据；
- 核心运行场景逐项通过；
- 无已知 P0/P1；
- 未验证环境明确列出；
- 开发者证据完成后由独立验收者复验固定提交；
- 用户确认可观察结果，而非被要求确认技术实现。

## 7. 常见失败模式

- 在 PRD 中塞入像素细节，却没有状态和运行步骤；
- 把 AI 参考图当确认稿；
- 使用 `Spacer`、绝对偏移或固定卡片高度局部修补，没有页面空间模型；
- 页面与系统导航同时承担安全区，产生重复空白；
- 只在 Preview 或单一模拟器看静态画面；
- 自动化测试只覆盖数据模型，却声称 UI 已通过；
- 开发对话自己截图、自己判断、自己批准；
- 修复一个设备后没有验证窄屏、最大字体和键盘；
- 视觉美化破坏旧版本的数据、手势或闭环。
- 按任务到达顺序逐张截图，没有先建立覆盖矩阵，导致同一状态重复取证。
- 仅因页面名字相同就复用截图，忽略 commit、数据、字号、键盘或滚动状态不同。
