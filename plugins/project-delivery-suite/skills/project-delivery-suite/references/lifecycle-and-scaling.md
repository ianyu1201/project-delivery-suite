## 1. 入口类型

### 新项目

从用户自然语言和已有素材提取：用户、问题、目标结果、载体、已知限制、排除项、成功样子。不要要求用户先写 PRD。先生成项目简报，再决定是否需要调研、原型或技术验证。

### 既有项目（brownfield）

先读取规则链、README、文档、代码入口、测试、Git、运行证据和已知问题。输出：

- 当前真实功能与架构；
- 文档/代码/运行态冲突；
- 不可丢失能力；
- 未提交和未验证状态；
- 最小治理方案；
- 当前适合进入的阶段。

不要因为用户说“从头开始”就丢弃已有事实，也不要把现有代码当最终产品定义。

### 新版本

读取上一版固定标签、版本交接、非回归矩阵、已知问题和当前运行证据。只对本版增量重新讨论，除非增量改变产品定位或基础架构。

若发现多个完整版本目录、不一致 PRD、已有未批准候选或待归档前序版本，切换到本 Skill 的版本治理模块并执行内部协作合同。总控模块不自行推断下一名称或建立完整版本副本。

### 缺陷/救援

冻结现场；记录复现环境、步骤、实际结果、预期结果、影响和证据。先恢复可信基线，再决定局部修复或重构。没有真实复现时标记为待验证，不凭截图或旧描述宣称根因。

## 2. 风险分级

规模代表交付治理强度，不代表项目价值。分别对以下维度打低/中/高：

| 维度 | 低 | 中 | 高 |
|---|---|---|---|
| 需求不确定性 | 单一清晰目标 | 多流程/部分开放问题 | 核心问题或边界未定 |
| 系统耦合 | 独立工具 | 多模块共享状态 | 多平台/多服务/软硬件 |
| 数据与安全 | 无敏感持久化 | 本地持久化/账号 | 支付、隐私、控制实体设备 |
| 迁移与兼容 | 无既有用户 | 需保留旧数据/行为 | 不可逆迁移或多版本共存 |
| 验证复杂度 | 少量路径 | 多状态、多设备/UI | 实机、现场、安全或法规 |
| 失败影响 | 可快速回退 | 用户数据/体验受损 | 人身、财务、生产或声誉风险 |

建议：

- 全低或仅一项中：小型；
- 多项中或一项高：中型；
- 两项以上高，或任何安全关键项：大型/高风险。

不要只用故事数或代码行数分级。向用户说明最关键的 2–4 条依据。

## 3. 阶段裁剪

### 局部交付与小型项目

目标明确、范围局部、可逆，无历史整合或待裁决产品/数据合同变化时，当前会话直接完成：

1. 读取相关代码、规则与已有授权，确认局部验收条件；
2. 实现并运行与改动风险相称的检查；
3. 说明结果、证据、未验证项和后续事项。

不强制新会话、完整 PRD、阶段章程或目录脚手架。无 UI 时 UI 合同不适用；没有创建任务时不生成 THREAD_REGISTRY。复用已有简报/Issue/交付说明承载必要范围；同一任务不建立平行权威文档。

新建小型产品仍需有足够明确的用户、范围和成功标准，但可在当前会话用简要记录完成 S0–S5。是否独立验收取决于风险、项目要求或用户明确请求；未执行时写 independent acceptance: not performed，不把自测当独立验收。正式版本批准仍由授权负责人决定，局部交付完成不自动代表正式发布。

出现重要产品决策、跨版本约束冲突、复杂数据迁移、安全或不可逆风险时升级流程，并说明触发原因；不要仅因文件数量增加而升级。

### 中型

- 产品与设计对话：S1–S3；
- 开发总控对话：S4–S5，在环境允许且已授权时按独立工作包分派子智能体；
- 独立验收对话：S6；
- 启动/产品对话：S7 和版本决策。

### 大型/高风险

按风险增加：版本总控、产品/研究、UX、架构/安全、工作包开发、系统测试、独立验收、发布。每个角色必须有独立可交付物；没有独立责任就不要创建角色对话。

## 4. 版本迭代

### PATCH

适用于恢复既有产品合同的缺陷修复，即使修复改变了用户当前观察到的错误行为，也可以是 PATCH。按风险选择局部验证、隔离分支/工作树与复验；仅正式补丁发布才需要标签。增加兼容的新能力才考虑 MINOR，破坏既有承诺则评估 MAJOR。

### MINOR

适用于向后兼容的新能力或体验改版。先由版本治理确定拓扑、名称和完整候选路径，再建立产品与设计、开发总控、独立验收阶段对话，显式维护上一版非回归矩阵。

### MAJOR

适用于破坏性行为、架构或数据合同变化。增加迁移、兼容、回滚、安全和发布阶段；不能只通过改版本号掩盖破坏性变化。

### 版本状态

统一使用：`idea → defining → contracted → building → active_candidate → validation_passed → accepted → version_approved/current → predecessors_archived → released/live_verified`。只有适用时才进入发布/现网状态。不要把 PRD 批准、分支存在、代码完成、测试通过、独立验收、版本批准、归档或已发布混为一谈。

## 5. 救援模式

当出现大量显眼缺陷、文档互相冲突、多个 AI 同时改动或无法确认当前版本时：

1. 暂停新增功能；
2. 固定当前 Git 状态和运行环境；
3. 建立已知问题与非回归清单；
4. 重建关键路径实际运行证据；
5. 区分产品缺口、设计缺口、实现缺陷和验收失效；
6. 先关闭 P0/P1，再恢复版本开发；
7. 把反复出现的问题写入合同或确定性门禁，不只写入聊天提醒。
