# Git 与版本控制

## 原则

- Git 是可恢复和可审计的事实层，不是装饰。
- 任何工作开始前记录当前分支、HEAD、未提交改动和 worktree。
- 用户既有改动归用户所有；不覆盖、不重置、不顺手整理。
- 一个工作包一个明确所有权；并行开发优先隔离 worktree。
- 提交前运行与风险相称的验证；每个提交只做一个逻辑变化。

## 默认策略

小型/单人项目优先短分支或直接在用户指定版本分支上做短增量。中型项目可使用版本集成分支加短期工作包分支。大型项目遵循现有团队策略，不强制改成模板模型。

示例：

```text
main                         已独立验收的稳定基线
release/v0.3                 当前版本集成（确有需要时）
feature/v0.3-search          短期工作包
fix/v0.3-search-navigation   缺陷修复
```

长期分支会积累冲突；工作包完成并验证后尽快集成。不要默认 force push、重写共享历史或自动删除分支/worktree。

## 基线与交接

每个阶段启动包记录：起点 ref、完整 commit SHA、工作目录、允许修改范围。阶段交付记录：终点 SHA、提交清单、未提交状态、验证结果和未集成依赖。

产品/设计冻结可建立带注释标签或等价不可变提交，例如 `v0.3-product-baseline`；最终通过建立消费者可理解的版本标签，例如 `v0.3.0` 或项目现行命名。标签不能代替验收报告。

## 语义版本

- MAJOR：用户/消费者依赖的合同发生破坏性变化；
- MINOR：向后兼容的新能力或体验升级；
- PATCH：不改变既有合同的修复。

0.x 项目也应明确自己的兼容承诺。版本号、标签、构建元数据和版本说明必须指向同一提交。

## 提交与差异

提交信息使用 `feat/fix/refactor/test/docs/chore` 等类型并解释意图。不要把产品文档冻结、共享架构重构、功能实现和大规模格式化混为一笔。

开发完成后至少检查：

- `git status` 和完整 diff；
- 是否包含密钥、缓存、临时截图或 IDE 私有文件；
- 修改是否超出文件所有权；
- 测试/构建是否对应当前提交；
- 证据是否确实由该提交产生。

## 发布状态

明确区分：`committed`、`reviewed`、`merged`、`built`、`active candidate`、`validation passed`、`accepted`、`version approved/current`、`predecessors archived`、`released/deployed`、`live verified`、`knowledge closed`。独立验收不代替版本批准，版本批准不证明归档已完成。只有适用状态都有证据时才能报告对应结论。

清理分支、worktree、临时库和旧候选物必须在完整汇报后由用户明确确认；优先保留可复核现场。
