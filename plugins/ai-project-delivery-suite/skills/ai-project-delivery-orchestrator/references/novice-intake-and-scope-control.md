# 非专业用户需求还原与范围控制

## 目录

1. 先还原意图
2. 锁定项目身份
3. 处理追加与纠正
4. 翻译绝对目标
5. 控制危险动作
6. 面向用户的回报

## 1. 先还原意图

用户不需要提供标准化 Prompt。Agent 从口语中提取：

- 对象：项目、绝对路径、仓库/worktree、版本、页面或交付物；
- 现状：已完成、正在进行、用户观察、Agent 推断；
- 目标：用户最终想看到的结果；
- 本步动作：分析、规划、修改、删除、创建、发布或验收；
- 不可变项：必须保留、明确排除、不得回归；
- 完成证据：文件、提交、测试、真实运行路径、截图或用户确认。

回复时先用日常语言复述这六项中会影响当前动作的部分。不要把用户的重复、情绪或非技术词汇当作缺乏目标；只处理会导致执行分叉的歧义。

## 2. 锁定项目身份

任何写入、治理、创建线程或 Git 操作前，建立项目身份四元组：

`project_id = 绝对根目录 + repo/worktree 身份 + 当前版本 + 当前阶段`

规则：

- 用户当前消息中的明确路径优先于旧记忆、旧摘要和同名目录；
- 同名项目存在多个目录时，先只读核对 Git 根、分支、HEAD 和权威入口；
- 回报中明确写出本轮操作对象；不得只写“当前项目”；
- 目标对象改变时，将其视为范围变化，不把旧目录上的动作自动复刻到新目录；
- 发现操作了错误对象，先停止、盘点已改内容和可恢复方式，再提出纠正方案。

## 3. 处理追加与纠正

用户说“开始之前再做一个任务”时，先分类：

1. **真正前置条件**：完成后才能推进当前阶段；
2. **独立并行项**：不改变当前门禁，可单独排期；
3. **后续优化**：进入 backlog，不阻塞当前阶段；
4. **目标替换**：明确关闭或暂停旧目标后切换。

用户说“不是 A，是 B”时，把 B 写为当前权威对象/需求，并检查 A 上是否已产生改动。用户只说“继续”时，先报上一个已完成检查点、下一动作及其完成条件，然后推进门禁允许的一步。

## 4. 翻译绝对目标

不直接承诺“完全没有 Bug”“所有问题解决”“与参考图一模一样”。把它们翻译为：

- 本版本合同范围和明确排除项；
- 允许/不允许遗留的缺陷等级；
- 自动化检查和关键真实运行路径；
- 目标设备、系统、屏幕、字号和数据状态；
- 与确认视觉基线的比较规则；
- 未覆盖环境、已知问题和发布建议。

向用户解释：目标没有被降低，只是变成了能检查、能复验、能关闭的标准。

## 5. 控制危险动作

“删除无用文件”“整理全部目录”“把记忆中的文件夹还原”等表达包含高风险判断。执行前必须：

1. 机械盘点候选对象；
2. 说明为何判定无用或错误变更；
3. 检查代码、文档、构建、脚本和外部引用；
4. 区分可直接忽略、可归档、可恢复删除和不可逆删除；
5. 给出精确清单与恢复点；
6. 获得覆盖该清单的明确授权。

不得把“让目录更简洁”解释为可任意删除，也不得因用户是非专业开发者而降低授权门槛。

## 6. 面向用户的回报

默认使用以下顺序：

1. **结论**：现在最值得做什么；
2. **依据**：已确认事实与仍是推断的部分；
3. **动作**：这一轮会做什么，不会做什么；
4. **关闭标准**：看到什么证据算完成；
5. **只在必要时提问**：仅询问会改变方向、授权或高风险范围的信息。

每轮只给用户一个清晰的下一步。内部可以维护完整状态机，但不要要求用户记住 S0–S7、Git 或测试术语才能继续合作。
